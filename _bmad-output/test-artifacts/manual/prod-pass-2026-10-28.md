## Coordinator's diagnosis of G6 (P1): "Ler visor" never reads in production

Facts, read on 2026-10-28 after part 2 found the gap:

- CloudWatch `/fasor/production/ocr`, last 14 days: the only `POST /read/display` requests are the nine of this pass (18:29 to 18:37 UTC), all `500`. No display reading was ever attempted in production before today, so no user could have reported it; Bruno has not used "Ler visor" on the tablet yet.
- Every failure is the same: `ResourceExhaustedError: Fail to alloc memory of 5648154624 size, error code is 12` (`cpu_allocator.cc:44`) inside the PP-OCRv5 **server** text detector (`services/ocr/app/detector.py`, `DETECTION_MODEL = "PP-OCRv5_server_det"`, `limit_side_len` 2000, `enable_mkldnn=False`, two CPU threads). The photo was 1200 x 900 px (the same size as the six display fixtures the sidecar's own tests read green on a developer machine), so the 5.6 GB is the server model's activation memory on CPU, not an oversized image.
- The instance is a `t3a.medium` (4 GiB; ECS registers 3851 MiB; 1227 MiB remained free during the pass). The ocr task reserves 1536 MiB soft with no hard limit; the api reserves 1024 MiB. `infra/README.md` already records the memory risk of a plate read coinciding with a document generation; a display read alone exceeds the whole instance.
- Plates and panels moved to Textract on 2026-10-05 (`OCR_PROVIDER=textract`, routing by reading kind in `apps/api/src/jobs/reading/providers/index.ts`); the display kind stays on `ocr-svc` by design because seven-segment digits are what the sidecar's PARSeq recognizer and `display.py` preprocessing were built for.
- The app degrades honestly: three attempts, then the failure state with "Digitar" keeping the sheet usable; no data is lost.

Options for Matheus (no infra change fits the budget: a `t3a.large` adds about USD 22 per month with the night schedule and takes the total from 83.27 past the USD 100 ceiling):

1. **Detector `PP-OCRv5_mobile_det`** in the sidecar (code: `detector.py` model name and the baked model directory in `services/ocr/Dockerfile`; rebuild the image; re-run `services/ocr` pytest on the six display fixtures and the plate accuracy test to see what the mobile detector loses). Memory in the hundreds of MiB. One batch touching `services/ocr` and its contract test; a deploy.
2. **Display reading through Bedrock vision** (code: a `display` structuring provider on the existing Bedrock client, the kernel's display parser fed by the model's digits instead of the sidecar's tokens; `OCR_PROVIDER=textract` routing sends `display` to it). Cents per reading like the plate; removes the sidecar from the production path (and its 1536 MiB reservation, which the api and LibreOffice would gain). Larger change, no image rebuild.
3. **Lower `OCR_DET_LIMIT_SIDE_LEN`** through the ocr task environment in `ecs.tf` (Terraform PR and apply). Cheapest to try, but unproven: the failing photo was already 1200 px, so a 960 px cap may still not fit in the 1.2 to 2 GiB available; a measurement under a memory cap on the local `ocr` profile image (which this host does not hold and would have to build) should come first.

Until one lands, "Ler visor" fails after three attempts in production and the engineer types the display values; the sheet, the burst start and the display-shot numbering are unaffected.
