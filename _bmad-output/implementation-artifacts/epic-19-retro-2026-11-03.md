- **Spec-to-implementation reconciliation:**
  - **S-1 (confirmed; same as R-1). The order key is not "the last synced edit".** The 19.2 DoR (`epics.md`, Story 19.2 DoR (3)) describes the summary's `updated_seq` as "the server's sequence of its last change, so an emitted relatório sorts by its emission and an active one by its last synced edit". EXPERIENCE.md § Home says the same. As built, the value is the `relatorio` entity row's own `updated_seq`:
    - `companySummary` reads it from that row (`apps/api/src/sync/pull.ts:161-176`).
    - The server writes `updated_seq: seq` only on the rows `applyOp` changed (`apps/api/src/sync/apply.ts:478-485`).
    - A block, reading, photo or checklist op changes block or file rows, not the relatório row. The relatório is named as a ref only for a site checklist or a carried library type (`packages/domain/src/ops/apply.ts:126-127`), and even then its row is written only when it changes.

    So an active relatório sorts by its creation, its last status change or its last setup edit, never by synced field work. Emitted relatórios do sort by their emission, as the DoR says. The AC text ("`updated_seq` descending") is met literally, but the DoR's reading of it is not, and neither is the intent behind Matheus's "mais recente". No test would catch the difference: every 19.2 test either writes `updated_seq` by hand or pushes only `relatorioCreateOp`s (`e2e/home.spec.ts:205-295`). Disposition: **spec reconciliation or a story; Matheus decides (E19-A1).**
  - **S-2 (accepted; recorded so later retros stop re-flagging it).** The 19.2 heading and its sprint-status key still say "capped with 'Ver todos'", although the page-size chips replaced "Ver todos". A dated note under the heading says so (`epics.md` Story 19.2, 2026-10-30), and the key is an identifier.
  - **S-3 (accepted).** The 19.2 DoD sentence "the first digest reads `home.status_chip` on Emitido and `home.page_size` per session" was narrowed with a date, because the events carry no tile and no size. Ledger row: `deferred-work.md` § Deferred from: Story 19.2 review (BH-4).
  - **S-4 (confirmed; same as R-2).** The 19.2 spec says "no change to the card itself". In fact the epic changed which card is current when two Em campo relatórios are on the device (R-2).

### Diff-scope review (`bmad-review`)

Three lenses ran in parallel over the code diff: adversarial (12 findings), edge case (9) and verification gap (2, plus a list of areas it checked and found clean). The boundary between 19.1 and 19.2 was weighted. The lenses were told that the 19.2 spec's Review Triage Log was already handled, so findings the story review had routed are not repeated here. Overlaps between lenses are kept and named.

- **R-1 (confirmed; adversarial 1, verification gap 1; same as S-1). The order ignores field work.** The adversarial lens's case: a Rascunho opened last week and captured every day since sorts below an untouched Rascunho created yesterday. With more than 10 active relatórios, the one being worked can fall off the first page. There are two ways out:
  - (a) The summary carries the relatório's last activity, for example `max(ops.seq)` per `relatorio_id` computed beside `relatorioTotals`. This is an additive summary field, so it needs a server change.
  - (b) A dated amendment says the order is the last change of the relatório's own row, and a test pins "a ficha edit does not move the card".

  **Matheus decides (E19-A1).**
- **R-2 (confirmed; adversarial 2, edge case 2, verification gap 2). The current card now follows the new sort.** `const current = cards.find((card) => card.status === 'em_campo' && states.has(card.id))` (`cards.ts:313-318`) runs on the array just re-sorted by `updated_seq`. Before Story 19.2, the current card was the on-device Em campo relatório with the latest service start. Now it is an unsynced one if any exists, and otherwise the one with the highest row sequence. With two Em campo relatórios on one tablet, `is-current` and the "Continuar" target can swap after any sync that touches the other one's header. No test puts two on-device Em campo relatórios together (the verification lens checked every `onDevice(` in `cards.test.ts`). Fix now (E19-A2): choose the current card by its own rule, independent of the list order. The default is the pre-19.2 rule, the latest service start, since the spec's "no change to the card itself" implies it. Add a kernel test with two on-device Em campo rows whose sequence order and service-start order disagree.
- **R-3 (confirmed; adversarial 3b, edge case 1 and claim 8). On a cold open, the first cut uses the wrong order.** `relatoriosPending` waits for the rows and the stored page size (`home-surface.tsx:88`), but not for the company summary. `summaryRelatorios` is `company?.relatorios ?? NO_SUMMARY` (`apps/web/src/state/sync.tsx:595`) until the `sync_state` live query answers. In that window no card has a sequence, so they all sort as "unsynced", by service start. Then they reorder, and the visible page of 10 can change which cards it holds. Holding the list until the page size is read was added to prevent exactly this kind of jump (triage row ECH-5). Fix now (E19-A2): the list stays pending until the company stream state has been read.
- **R-4 (plausible; adversarial 3a). "No summary entry" is read as "created here".** A relatório removed on the server drops out of the summary (`isNull(entities.removed_at)`, `pull.ts:163`). Its local row is tombstoned only when its stream pulls. Until then, it sits right after the current card as "the newest". Defer (E19-A3): mark the unsynced bucket with a positive signal, a pending `relatorio` create op in `outboxByRelatorio`, not with a missing sequence.
- **R-5 (confirmed; adversarial 5, edge case 3 and 4). The keyboard path clicks every time.** `moveTo` now calls `chip?.click()` (`chip.tsx:96-100`). Home on the first chip, End on the last, and every key repeat while an arrow is held each fire a click. The document listener records each one as a `home.page_size` action, even when the selection did not change. And when a chip's ref is missing, the old `onChange` fallback is gone. The tap case was rejected in triage (ECH-4). The keyboard case is new: the ECH-3 patch introduced it. The verification lens checked the other four consumers (the gallery, the not-tested dialog, the move-block dialog and the field fixture). None has a `[data-telemetry]` ancestor, and the chips are `type="button"`, so these surfaces get no new event and no form submit. Fix now (E19-A2): click only when the target differs from `selectedId`, and keep the `onChange` fallback for a missing ref.
- **R-6 (confirmed; adversarial 6). Two kernel functions take a `filter` whose `null` means opposite things.** In `homeCards`, `filter: null` means every card (`cards.ts:321`). In `homeList`, `null` means the active statuses only (`cards.ts:376-378`). Production no longer passes a non-null `filter` to `homeCards`. `homeList` assumes its input is the unfiltered set, since `cards.length === 0` decides the `none` state. Defer (E19-A3): drop `filter` from `HomeCardsInput`, or rename `homeList`'s option to `tile`, and document the input contract.
- **R-7 (confirmed; adversarial 7). `HOME_ACTIVE_STATUSES` is a hand-written list** (`cards.ts:325`). Nothing ties it to `RELATORIO_STATUSES` (`status/table.ts:14`), so a status added later would silently drop out of the default list. Fix now (E19-A2): derive it as every status except `emitido`, or pin it with a kernel test.
- **R-8 (confirmed; adversarial 8, edge case claim 9). The 19.1 viewport check passes on one pixel.** `e2e/app-layout.spec.ts:43-44` uses `toBeInViewport()` with the default ratio of 0, at a height of 900 px and with no relatórios seeded. The AC asks for both cards "in the viewport without scrolling" with "any number of relatórios". Fix now (E19-A2): use `toBeInViewport({ ratio: 1 })`, and optionally seed more than 10 active relatórios.
- **R-9 (confirmed; adversarial 9). Matheus's "A" is unit-tested only.** No component or e2e test creates a relatório on the device and checks its place, and `19.2-E2E-001` never asserts `.is-current` in the mixed active list. AGENTS.md: "a feature with a front end runs through Playwright as a human would". Fix now (E19-A2): extend `19.2-E2E-001`. Create a relatório through "Novo relatório" while the push hangs, then assert its place and the current card.
- **R-10 (plausible; adversarial 4 and 10). The page size has no optimistic state.** `selectedId` comes from IndexedDB through the live query only (`home-surface.tsx:82,256-262`). A quick tap on 20 and then 10, or an arrow held down on a loaded tablet, can leave the focused chip and the stored size out of step. A failed `writeHomePageSize` is swallowed (`.catch(() => undefined)`) after the telemetry listener has already counted the tap. Defer (E19-A3).
- **R-11 (confirmed; edge case 7). A failed `readHomePageSize` takes down Home.** The live query has no catch (`home-surface.tsx:82`), so a rejected read of a cosmetic preference rethrows during render. Fix now (E19-A2): `readHomePageSize(db).catch(() => DEFAULT_HOME_PAGE_SIZE)`.
- **R-12 (confirmed; adversarial 11). Screen readers do not hear the note change.** "Mostrando n de N relatórios" is a plain `<p>` (`home-surface.tsx:255`). The gallery's FilterChipGroup, the precedent, pairs its chips with a visually hidden `role="status"` line (`gallery-surface.tsx:280`). Fix now (E19-A2): use the same pattern.
- **R-13 (plausible; adversarial 12, edge case 5 and 6). The size control sits only below the list.** After 50 or 100 is chosen, the chips are at the end of a long list. Choosing a larger size inserts cards above the focused chip. If a sync drops the selection to 10 or fewer, the chip group unmounts while it has focus. The stored size also makes every later visit open long, which works against the epic's goal of a short Home. This is a UX question rather than a defect of the as-built, since the mocks draw the note under the cards. Defer to Matheus and Sally (E19-A3 ledger row; Open questions).
