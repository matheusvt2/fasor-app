## Intent

**Problem:** The op log of Story 1.4 stops at the device outbox and the server materializer: nothing pushes an op to the server, nothing pulls what the office or a colleague changed, a rejected op has no way to leave the device's state, and no screen can trigger or show a sync. Every later story (Home freshness, capture, photos, generation) assumes the device and the server converge by themselves.

**Approach:** Ship the typed sync contract in `packages/domain/contract` (routes, `CONTRACT_VERSION`, error codes, example fixtures), the three server routes (`POST /api/sync/ops`, `GET /api/sync/company`, `GET /api/sync/relatorios/{id}`) over the existing `applyOps` with origin-aware rejection, `superseded` and `last_push_at`, and the device engine in `apps/web/src/sync` that runs one fixed cycle (push → pull company → pull each relatório) on launch, on `online`, every 60 s and on "Sincronizar agora". The device keeps the server's log per entity in a `remote_ops` table and re-materializes an entity as `replay(remote ops in seq order)` then pending outbox ops on top, which gives rebase, dead-op exclusion and device/server convergence from one function. A minimal Sync status surface, Sync badge, 426 "Atualizar" state and the pending-sync sign-out wording complete the story.

## Boundaries & Constraints

**Always:** `packages/domain` stays pure (zod only) and computes every status, count and text once: `syncCounts`, badge state, pending-summary text and `materializeEntity` live there. `applyOp` remains the only reducer; the device never applies a pulled op except through `applyOp`, routed by `op.scope`, never by the stream it came from. `apps/web` calls the network only from `src/sync` (engine and client) and imports Dexie only inside `src/db`; the UI reads through `useLiveQuery`. The client speaks to the server only through the zod route definitions in `packages/domain/contract`, sending `CONTRACT_VERSION` in the `x-contract-version` header; every failure body is `{code, message, details?}` with a code from the contract enum. The server rejects an op only for shape (`op_invalid`, `op_path_unknown`), server-only family or origin (`op_server_only`) or tenant (`op_tenant_mismatch`), never for a domain rule; per-op atomicity; `seq` monotonic per company under the existing advisory lock. A rejected op becomes `outbox.status = dead` with its code, keeps its value and leaves the materialized state. Rebase: after any pull, every non-dead outbox op still applies on top of the pulled value, `prev_op_id` untouched. The pull cursor never passes an op the device cannot parse; `426 contract_outdated` is answered only by pulls, stops pulling without moving the cursor, keeps pushing and shows the full-screen "Atualizar" state. Retry: network and 5xx with backoff and jitter; 4xx never, except `401` (re-auth banner, outbox intact). Dexie versions append-only with `upgrade()`; Drizzle migrations forward-only via `pnpm db:generate` in the container. English identifiers; pt-BR copy marked `// authored:` when not from a mock; no emoji; no `fasor` in web strings; `PRODUTO` only. Everything through `docker compose` (project from `{WT}/.env`).

**Never:** No file upload, `PUT /api/files`, thumb prefetch or `files_pending` logic (Epic 6). No merge policy, Conflict view or `conflict` badge state beyond the type (deferred by the spine); `superseded` is parsed and shown as a count for the session, not persisted. No Home cards, status tiles, `progress`, theme, storage rows, `unsynced-5-days` or `offline` banners, toast component or badge live-region announcements (Story 1.6). No service worker or drafts (Story 1.8). No pre-issue list or Sumário (Epic 5): the dead-op count and "Reenviar" live on Sync status here. No server-side emitter of server-only families (no caller passes `origin: 'server'` yet). No new env variable for the contract minimum; no per-relatório `title` column; no separate `relatorio` SQL table (the `entities` row is the relatório). No test-only sync hook (`window.__releng`): TC-4 is the visible button.

## Design Notes

**The device keeps the server log (`remote_ops`) and re-materializes from it.** AD-24 phrases both rebase and dead-op exclusion as "`applyOp` re-runs over the log minus dead ops for that entity", and 1.5-E2E-001 requires the device and server snapshots to be equal after a sync. An incremental apply of pulled ops onto the local row cannot do either: it has no way to remove a dead op's effect and it keeps the device's pre-coalescing `first_edited_at`. So every pulled op is stored once in `remote_ops` (primary key `op_id`, which is also the cross-stream dedupe), and an entity's local row is always `materializeEntity(ref, remote ops of the ref in seq order, non-dead outbox ops of the ref not yet in remote_ops)`. Rebase, dead exclusion, Reenviar and convergence are then the same function. Implementers may apply pulled ops incrementally for refs that have no outbox rows (identical result); the tests compare against the pure function.

**Coalescing fork: option (b).** Story 1.4 left "(a) do not coalesce across the first edit" or "(b) re-materialize on pull" to the architect. (b) is what the design above does without any extra code: once a block's own ops are acked and pulled back, `first_edited_at` is derived from the server log. Until then the device shows its local value; the shift is one coalescing window (500 ms idle to a few seconds) and only on that column. (a) would alter AD-3's coalescing rule, which needs a `source-deltas.md` row this story must not write. Recorded in `deferred` so the architect can still choose (a); the 1.4 pin test is replaced by the convergence test.

**Outbox status lifecycle.** `pending` → `sent` (request in flight) → `acked` (server answered with `seq`, stored on the row) or `dead` (code stored). `sent` rows found at launch are pushed again; the server dedupes by `op_id`. `acked` rows stay in the outbox (undo needs `prev_value`) and drop out of materialization once the same `op_id` is in `remote_ops`; `materializeEntity` excludes local ops whose `op_id` is among the remote ones, so the "not yet pulled back" window needs no extra flag.

**Origin on the server.** `applyOps` never sees a cookie, so the route tells it `origin: 'client'` with the session's `actorId`. For a client origin a server-only family, `device_id = server` or a `system:*` actor is `op_server_only`, and an `actor_id` other than the session user is `op_invalid` (a forged attribution is a shape error, not a tenant one). No caller passes `origin: 'server'` yet; the parameter is required so the next emitter (Epic 6 files) must state it.

**`superseded` is computed per path on the server.** The latest `op_id` on `(company_id, path)` is read inside the same per-company transaction before the insert; a `prev_op_id` that differs (or is null while the server has one) is applied and reported. The device shows the count for the session on Sync status and persists nothing: the merge policy that would interpret it is deferred by the spine.

**Pull paging with `{ops, seq, summary?}` only.** `seq` is the stream head at the time of the pull, not the last op returned; the device loops while its cursor is below the head and records `complete = cursor >= head`. That keeps the response to the three keys the AC allows and still tells the device when a relatório is fully on the device (Story 1.6's "No aparelho").

**Which relatórios are pulled.** The company summary lists the company's relatório rows (from `entities`), which is the "minimal relatório row needed to scope a stream" of the AC; no `title` exists on the row and none is added. The engine pulls every relatório in `rascunho` or `em_campo` and every relatório that already has a `sync_state` row (opened before); Story 1.6 adds pull-on-open for the other statuses and the card states.

**Sync status is the headline of Epic 10's surface.** Story 1.6 says "rows beyond the headline arrive in Epic 10"; this story renders the headline, the primary "Sincronizar agora" (the AC's placement wins over the mock's foot text button), the dead-op row with "Reenviar" (the AC keeps the value "for Reenviar" and E2E-002 needs a visible place before the Sumário exists), "Último envio" and the foot. The badge announces nothing yet; Story 1.6 owns the live region and the tap-to-open polish beyond the link.

**`x-contract-version` is required on pull, only sent on push.** The AC reads "426 contract_outdated on pull stops pulling, keeps pushing": a pull without the header or below `MIN_CONTRACT_VERSION` answers 426; a push carries the header (the client always sends it) but the server never enforces it, because families and routes are append-only (AD-13) and an outdated client's ops are still valid ops. Enforcing it on push would break "keeps pushing" and leave work stranded on the device. 1.5-API-005 pins both halves.

**Tenant-scoped op_id dedupe.** `op_id` is globally unique in `ops`, so the dedupe lookup after a no-op insert is scoped by `company_id` (AD-10): an op whose id already exists under another company is rejected `op_invalid` (it can never be inserted), instead of answering the other tenant's `seq`, which would have made the device mark it `acked` and lose it silently.

**The 426 state has no mock.** It is rendered like `Booting`: a full-surface replacement of the shell, plain elements, `.btn` primary "Atualizar" that reloads. Copy is authored and marked as such; a UX pass may replace the strings without touching behavior.
