#### Adversarial lens (R-A)

- **R-A1 (confirmed). A 429 deletes the batch.** `apps/web/src/telemetry/flush.ts:60-66` keeps rows only on a network failure or `status >= 500`; the limiter in `apps/api/src/http/telemetry.ts:26,67-72` allows 1000 events a minute per `user:device`, and `drain` posts up to 26 batches of 200 back to back. A device that reconnects with more than 1000 queued events (a day of field work, exactly what the epic wants to read) loses every batch after the fifth: up to 4000 of its 5000 events. The DoR's "delete on any 4xx" and its own per-device limit contradict each other. Fix now: keep the rows on 429 and end the flush; the next `ran` cycle resumes a minute later. Upstream: a refusal the server itself schedules (429) is never a "drop" code.
- **R-A2 (confirmed by design). One unknown event refuses the whole batch and the device deletes it** (`telemetry.ts:61-63`, `flush.ts:64-65`). Reachable only when a bundle and the api disagree on a closed list: the lists are append-only in practice, so the window is the minutes of a deploy, and the api's request log shows the 400. Defer: a rule line under "Adding an event name" (names are appended, never removed within a release) and a ledger row; a per-event parse stays an option if the drift ever shows.
- **R-A3 (confirmed by design). A sink failure still answers 204** (`telemetry.ts:81-86`, `sink.ts:80-83`; AD-28: events are not records). A role or group misconfiguration loses every event while the smoke and `/api/health` stay green; the only sign is `ux_event_sink_failed` in the api log. Fix now (E18-A2): the deploy's smoke gains a telemetry step (a `session_start` with the deployed tag in the group, no `ux_event_sink_failed` since the deploy; same step closes R-V12 and R-V13); the digest procedure greps the api log for the failure line (E18-A3).
- **R-A4 (confirmed). No timeout on the telemetry fetch** (`apps/web/src/api/telemetry-client.ts:10-20`), and `running` holds every later flush until the promise settles (`flush.ts:35,77-86`); the api's `CloudWatchLogsClient({})` has SDK defaults. A stalled connection freezes the queue for the app's life (same as R-E5). Fix now: `AbortSignal.timeout(15_000)` on the device; `maxAttempts` and a request timeout on the client.
- **R-A5 (plausible). Two tabs share one queue** and both post the same oldest rows (`flush.ts:33-35`: module state per tab). Rare on a tablet PWA; possible on a desktop review. Defer: Web Locks around the drain, ledger row.

The rows are not lost (they go with the next sync) but may land on the next day. Fix now (one line): `pagehide` beside `visibilitychange`; defer the synchronous mirror (ledger row).
- **R-A7 (confirmed). The telemetry route sits under the shared 16 MB JSON body limit** (`apps/api/src/http/app.ts:127,182`) while a valid batch is about 120 KB. Fix now: a 256 KB `bodyTooLarge` on `TELEMETRY_ROUTE.path`.

The smoke company's sessions are counted in every view.** `var.smoke_company_id` exists (`infra/production/variables.tf:185`) and no query filters it; today's smoke device wrote 57 events, this session's device 74, against 12 from the two real devices. Fix now (E18-A2): `filter company_id != '${var.smoke_company_id}'` prefixed to the nine queries.
- **R-A9 (confirmed). `sessions_per_day` bins by `@timestamp`, the batch's `received_at`** (`sink.ts:78`, by ECH-1's fix), so a device that syncs after days offline puts its sessions on the sync day. One `sync_result` row and one `POST /api/telemetry` per `ran` cycle.** `observeCycle` (`sync.tsx:257-262`) tracks and flushes on every cycle that ran; the engine runs a cycle every 60 s while the tab is visible and every 5 s while a reading is pending (`engine.ts:164,173,710-711`), and an empty outbox still pulls, so the cycle is `ran`.
