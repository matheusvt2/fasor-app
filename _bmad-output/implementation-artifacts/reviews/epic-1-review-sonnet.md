# Epic 1 Review — Sign in and work on the device (offline-first foundation)

Reviewer: sonnet (independent review, one of three parallel reviews feeding the epic retrospective)
Scope: PRs #1-#8, main branch, HEAD `00de851`. Read-only review; no code, docker state or DB touched.

## Executive summary

Epic 1 delivers a genuinely solid offline-first foundation: the op-log/`applyOp` reducer, the Dexie schema, the sync engine (push/pull/rebase/rejection), better-auth session handling, tenant scoping, the service worker and the shared component library all match the architecture spine closely, with unusually good self-documentation (comments cite AD numbers and explain *why*, not just what). Direct code inspection plus two independent architecture audits found **zero hard architecture-rule violations** among AD-1, AD-2, AD-3, AD-4, AD-8, AD-9, AD-10, AD-22, AD-23 and AD-24; everything not yet applicable (pre-issue/Sumário, file uploads, suggestion emitters) is correctly deferred to later epics. Test quality is high: descriptive story-numbered test names, a real Dexie/Postgres replay byte-equality test, a Drizzle migration-drift test, and Playwright specs that use "Sincronizar agora" rather than the 60 s timer. The two most important gaps are process, not code: the PRD Q0 real-device offline proof required by Story 1.8's own acceptance criteria has **never been run** (only a `PENDING` template exists), and Account's professional-registration save still bypasses the op log via a named REST action not on AD-1's allowed list, a documented-but-unresolved carry-over from when Stories 1.2-1.4 were built in parallel. Several other deferred items (Toggle/Checkbox visual-fill gap, Login not yet swapped onto the shared `Button` component, coalescing vs. `first_edited_at` disagreement) are real, tracked, and low urgency individually, but add up to a debt list that should be triaged before Epic 5 wires them into real capture surfaces. The independent PR reviews caught several genuine defects the internal four-layer automated review missed, including one cross-tenant data-loss bug (PR #6) and a Host-header session-hijack vector (PR #5) — both fixed before merge. Overall: a strong, unusually well-reasoned Epic 1 delivery, with unglamorous but real follow-up work before Epic 2 leans on it further.

## 3. Cross-story seams

- **Two copy modules, not the one Story 1.2 asked for.** `apps/web/src/copy/ui.ts` (component-level generic strings: toggle on/off, confirm-dialog cancel, overflow-menu label) and `apps/web/src/copy/pt-br.ts` (`copy.login.*`, `copy.account.*`, `copy.home.*`, `copy.sync.*`, ...) both exist and are both actively imported (`ui.ts` by 7 component files, `pt-br.ts` by 17 surface/state files). Story 1.2's own AC (epics.md:551) calls for "a single pt-BR copy module." The split is functionally defensible (component-owned generic labels vs. surface-owned sentences) and each file documents its own scope, but it is in tension with the AC's literal wording and is exactly the kind of thing that invites a third copy module in Epic 2 if nobody calls it out. Recommend explicitly re-scoping the AC or merging the two before more surfaces land.
- **Login was never swapped onto the shared `Button` component.** `apps/web/src/surfaces/account/account-surface.tsx:11,223` imports and uses `Button`/`SegmentedControl`/`TextButton` from `apps/web/src/components`; `apps/web/src/surfaces/login/login-surface.tsx:102-124` still hand-rolls `<button className="btn btn-primary btn-block" aria-disabled={...} aria-describedby={...}>` and a separate `<button className="input-suffix-btn">` for "Mostrar" — reimplementing, without a test, the exact `aria-disabled`+`aria-describedby` invariant that `components/button.tsx`'s `assertReason` enforces at runtime. This is not an oversight: `spec-1-3`'s Design Notes explicitly say Login/Account were built "from plain elements... so 1.2's components can replace it mechanically" because 1.2-1.4-1.7 were being built concurrently, and PR #5's review follow-up explicitly punts the swap to Story 1.6 — but Story 1.6 only swapped Account, not Login. Concrete, low-risk, low-effort follow-up.
- **Toggle/Checkbox visual-fill gap, still open.** Confirmed directly in `toggle.tsx:11-25` and `checkbox.tsx:8-17`: both components' own doc comments describe the exact CSS/DOM-shape mismatch (`components.css` keys the "on" fill to `[aria-checked]`/`[aria-pressed]` on the *visible* element; React Aria correctly puts that state on a hidden native input instead). `SegmentedControl` was fixed by being hand-rolled outside React Aria specifically to route around this (`segmented-control.tsx:11-25`); Toggle and Checkbox were not, and are not yet used by any real screen, so nobody has hit it in a browser yet. This is `components.css`/DESIGN.md-authority work the story that shipped it explicitly said it couldn't do alone — a design-system decision the retro should assign an owner to before Epic 5's checklist UI needs `Checkbox`.
- **`user/{id}/{field}` op family exists but has no writer.** `packages/domain/src/ops/path.ts:123,242` registers the family; nothing in `apps/web` ever emits it (see §1/§2's registration-save note). A family with zero emitters is harmless today but is exactly the kind of thing that should either get a caller in the next story that touches Account, or be flagged so it isn't mistaken for "already done."
- **Coalescing vs. `first_edited_at` is an unresolved architectural fork, not a bug.** AD-3's outbox coalescing keeps the *last* `client_ts`; AD-18's `first_edited_at` is meant to be the first-applied op's timestamp. Story 1.4's own spec measured the divergence (device outbox shows 10:26, server-replayed materialization shows 10:27 on the small fixture; 64 live ops fold to 63 outbox rows) and left the choice ("don't coalesce when it would erase the block's `first_edited_at`" vs. "re-materialize on pull") to the architect; Story 1.5 implemented the pull-side re-materialize as the working behavior, but a `deferred` entry says the coalescing-side option is still open. Since `first_edited_at` isn't rendered or tested against real sheet data before Epic 5, this is safe to leave open for now but should be closed before Epic 5 starts, not discovered mid-story.
- **No FK from `ops.company_id`/`entities.company_id` to `company.id`.** `apps/api/src/db/schema.ts` declares `company_id` as a bare `uuid` column with no `.references()` on either the `ops` or `entities` table; PR #5's review follow-up explicitly notes this was left out on purpose ("later story"). Tenant scoping is enforced entirely at the application layer (AD-10's own text allows this — "Row-level security is deferred, not replaced" — and the app-level test suite is solid), but a dangling FK-less `company_id` is worth a one-line reminder in the deferred list so it doesn't get lost.
- **Dexie schema evolution.** `apps/web/src/db/schema.ts:108-151` is genuinely append-only, four versions, every version has a real `upgrade()` (v3's is a real data backfill, not a no-op stamp), and `LATEST_VERSION`/`upToVersion` parameterization exists specifically to support the "outbox survives upgrade" test. No issues found.
- **Drizzle migrations chain and drift test.** `apps/api/src/db/migrations-match.test.ts` regenerates migrations from `schema.ts` into a scratch folder via `drizzle-kit generate` and diffs the file list/stderr against the committed migrations — a real drift guard, not a placebo (it accounts for drizzle-kit 0.31's "exits 0 even on failure" behavior by asserting on output content, not exit code). Good practice, worth calling out positively.
- **docker-compose profiles and port parametrization.** `prod`-profiled services (`migrate`, `api-prod`) are cleanly isolated from the default dev services; every host port that could collide across parallel worktrees (`CADDY_HTTP_PORT`, `CADDY_HTTPS_PORT`, `API_PROD_PORT`) is env-parametrized with sane defaults — and this was itself a fix the independent PR #2 review forced (the first draft hardcoded 80/443/3001). No outstanding issue.
- **`Dockerfile.tools`.** 12 lines, `node:24-bookworm` + Playwright's `chromium`/`webkit` install + pnpm activation. Lean; no bloat found.
- **Dev-only fixture route.** `apps/web/src/surfaces/fixtures/field-fixture-surface.tsx` mounts at `/__fixture/field`, is explicitly `import.meta.env.DEV`-guarded (absent from production builds), and exists specifically because no real capture surface exists before Epic 5 to exercise the durability machinery against. This is a well-reasoned, well-documented stopgap (the file's own header comment explains exactly why and what replaces it), not scope creep — flagging only so the retro tracks that Epic 5 must delete/replace it as documented.
- **Error envelope consistency.** Every error path across `apps/api/src/http/*` and `apps/api/src/sync/*` uses the same `{code, message}` shape (`ErrorResponse` from `packages/domain/src/contract`); no divergent envelope found.

## 4. Test quality

Directly verified: 77 unit/integration test files under `packages/domain/src`, `apps/web/src`, `apps/api/src`, plus 6 Playwright spec files under `e2e/` (`account.spec.ts`, `auth.spec.ts`, `durability.spec.ts`, `home.spec.ts`, `shell.spec.ts`, `sync.spec.ts`). Breakdown by area (domain 22 files/273 tests, web 46 files/316 tests, api 9 files, e2e 6 files), and by story-tag prefix (10× `1.8-E2E`, 8× `1.4-UNIT`, 8× `1.3-E2E`, 6× `1.5-API`, 5× `1.6-E2E`, 5× `1.5-UNIT`, 4× `1.4-INT`, 4× `1.3-API`, 3× `1.6-UNIT`, 3× `1.5-E2E`, plus 2× `1.8-UNIT`/`1.8-AC`), independently confirmed against PR #8's reported totals (581 unit, 54 api, 21 e2e `@p0`).

- **`pnpm verify` definition** (`package.json:20`): `lint && static && test:unit && test:api && test:e2e`, where `test:e2e` is `playwright test --grep @p0 --project desktop-chrome --project durability-desktop-chrome` — matches Story 1.1's AC and AGENTS.md's description. **No timing evidence lives in the repo** (there is no CI, so no captured run history); the only "under 15 minutes" evidence anywhere is PR #8's pasted verify output (green in 238 s) — real, but a single self-reported data point, not a monitored budget. `docker compose run --rm tools pnpm lint` and `pnpm static` were re-run live for this review and passed clean; the domain+web slice of `pnpm test:unit` (273 + 316 = 589 tests) was re-run live and passed in ~56 s combined, corroborating that the unit layer alone is fast.
- **`pnpm test:unit` is not actually a pure-unit command.** Its second half (`vitest run` at the repo root, `package.json:11`) picks up `scripts/tooling.test.ts`, whose `'provisions the two test companies through the CLI'` test spawns `pnpm exec tsx scripts/seed-users.ts --test` against the ambient `DATABASE_URL` — i.e. it writes real seed rows into whatever Postgres the container is pointed at. Inside `docker compose run --rm tools`, that's the disposable `tools`-profile stack, so this is safe in the intended invocation, but the script name promises something narrower than what it does, and it is easy to invoke this outside a disposable environment by mistake. Worth a rename or a split (`test:unit` vs. `test:tooling`) rather than a behavior change.
- **The docker-compose-only reset script is real but is not what Playwright's own suite calls.** `scripts/test-reset.ts:12-23` (`assertInCompose`) exists exactly as Story 1.1's TC-9 AC describes and is itself unit-tested (`scripts/tooling.test.ts:61-76`, including a real subprocess spawn asserting the guard fires). But `playwright.config.ts:17`'s `globalSetup` (`e2e/support/global-setup.ts`) calls a *different* function, `resetTestCompanyData` (`apps/api/src/db/seed.ts:172-179`), in-process, with no `assertInCompose` guard, once per full Playwright invocation rather than per suite. Both ultimately only clear `ops`/`entities`/`sync_device_push` today (`test-reset.ts`'s wider `TABLES` list — `files, revisions, generation_jobs, reading_runs` — silently no-ops via `to_regclass` because those tables don't exist yet, a still-open item in `deferred-work.md`), so the two paths are equivalent in practice, but the AC's guarded script isn't actually the mechanism gating Playwright determinism — that's worth correcting in the AC or the docs, not just the code.
- **Determinism, otherwise good.** Where sync is under test, Playwright clicks "Sincronizar agora" rather than waiting on the 60 s timer (`e2e/sync.spec.ts`, `e2e/durability.spec.ts:174-177`, `e2e/home.spec.ts`), including a deliberately slowed route (`page.route(...)` + a 2.5 s injected delay) used to make an in-flight state observable — an engineered deterministic delay, not a hope-based sleep. The 60 s interval itself *is* unit-tested deterministically in `apps/web/src/sync/engine.test.ts:282-298` against a hand-built fake clock (not vitest's global fake timers, which the test's own comment says "would also freeze the scheduling fake-indexeddb relies on") — a genuinely careful piece of test infrastructure. One real flaky-pattern instance found: `e2e/durability.spec.ts:284-286` (`1.8-E2E-005`) follows a deterministic `expect.poll` (waiting for a positive "the gate ran" signal) with a bare `waitForTimeout(1_000)` before asserting a *negative* (no further worker message posted) — there's no positive signal for "the gate has now finished deciding not to post," so this one assertion is structurally timing-dependent, though the code's own comment is candid about the tradeoff. A handful of other `waitForTimeout` calls are either a bounded poll (`e2e/support/outbox.ts:141`, 40 retries × 100 ms for `device_id` to land) or a documented "give the write a turn" yield (`e2e/support/durability.ts:121`, 300 ms after firing `visibilitychange`) — lower-risk than the first.
- **FR-54 scenario coverage — two of three are fully real, the third is half-real and honestly says so.** All three exist as separately named `@p0` tests in `e2e/durability.spec.ts` and pass on desktop Chrome, Android Chrome emulation and WebKit (PR #8's matrix: 18/18). "Tab closed mid-sheet" (`1.8-E2E-001`, lines 48-90) does a genuine `page.close()` + `context.newPage()` reopen, not a re-render. "Network dropped mid-push" (`1.8-E2E-002`, lines 140-195) uses `page.route` to let the request actually reach and be applied by the real server (`route.fetch()`) and then aborts delivery of the *response* (`route.abort('internetdisconnected')`) — the worst-case "server applied it, client never heard back" scenario — then asserts exactly one server row and one acked outbox row per op, proving no double-apply. "Quota exhausted via mocked `storage.estimate`" (`1.8-E2E-003`, lines 197-220) is **only half what its name says**: the test does monkey-patch `IDBObjectStore.prototype.put` to throw a real `QuotaExceededError`, and that half is genuinely exercised (toast shown, value not lost, retry succeeds once "freed"); but `e2e/support/durability.ts:140-149`'s own comment states the `navigator.storage.estimate` mock installed alongside it is a "PLACEHOLDER: nothing in the app reads this yet" — no test asserts against it, because no surface calls `storageHeadroom()`/`storageLow()` yet (tracked as its own deferred item, §6). This is honestly documented dead code, not a faked pass, but the scenario as named is not fully implemented. Separately, two other honest gaps: the network-drop scenario only covers the op-log push half (no uploader exists yet for the file half), and the tab-close/cold-open scenario is annotated `not-covered-here` on the WebKit project specifically (Playwright's WebKit cuts the network below the service worker, so the SW's offline path can't be exercised there at all) — both point back to the still-pending manual iPad/Android run (§1, §6) as the place this class of behavior actually gets proven.
- **Kernel and cross-layer test depth.** `packages/domain/src/ops/apply.test.ts` asserts referential identity (not just value equality) to prove a second `create` on the same id is a true no-op (`expect(...).toBe(...)`, not `toEqual`), and includes a genuine schema-rejection case with a malformed value. The AD-3 replay test is a real three-way byte-equality check (`toBe`, i.e. string identity, on serialized JSON) between the pure kernel replay, the Drizzle-materialized snapshot, and a checked-in golden fixture (`apps/api/src/sync/replay.integration.test.ts:34-52`, mirrored on the Dexie side in `apps/web/src/db/commit.test.ts:67-79`) — not one path trivially compared to itself. The AD-10 cross-tenant suite (`apps/api/src/sync/sync.integration.test.ts`) goes beyond a same-shape unit test: it interleaves real pushes from two seeded companies and asserts each keeps an independently monotonic `seq`, and adds a compile-time half via `@ts-expect-error` (caught by `pnpm static`, not a runtime test) proving a repository call that omits `company_id` fails to typecheck at all. The Drizzle migration-drift test (`migrations-match.test.ts`) diffs `drizzle-kit generate`'s actual file/stderr output rather than trusting its exit code, which the test's own comment flags as unreliable (drizzle-kit exits 0 even on a broken invocation).

No hard-coded-value-instead-of-behavior anti-pattern or inert/always-succeeding mock was found in any of the files sampled. Overall test quality is a clear strength of this epic, with two concrete process nits (the `test:unit`-touches-real-DB naming mismatch, and the AC-described reset script not being the one Playwright actually calls) worth cleaning up rather than leaving to be rediscovered.

## 7. Process observations

- **Spec sizing.** Every feature story (1.2 through 1.8 — all but the scaffolding story 1.1) carries an `oversized` warning in its own frontmatter. This is a systemic sizing signal worth discussing in the retro on its own terms, not a one-story fluke.
- **What the internal 4-layer review missed that the independent review caught** (all confirmed directly in PR bodies via `gh pr view N --json body`):
  - **PR #4 (Story 1.2)**: `aria-disabled` set on the `<ComboBox>` wrapper was silently dropped by react-aria-components before ever reaching the DOM — a different and more fundamental bug than the `aria-describedby`-wiring gap the internal review had already found on the same component. Fixed by moving the attribute onto the inner `<Input>`.
  - **PR #5 (Story 1.3)**: a live-reproduced 5xx (database taken down) rendered as "Senha incorreta" even after the internal review's own network/credentials split was already in place — the split's 4xx/5xx boundary was wrong, not missing. Fixed alongside the Host-header trust bug (§5).
  - **PR #6 (Story 1.5)**: op_id dedupe wasn't tenant-scoped — a company reusing another company's already-applied `op_id` would be told "applied" with the *other* company's `seq`, and its device would mark the row `acked` locally with nothing written to its own tenant. A silent cross-tenant data-loss bug in AD-10 territory that Story 1.5's four internal review layers — which did check `company_id`-field mismatches — did not reach. Fixed by scoping the dedupe lookup to `(op_id, company_id)`.
  - **PR #7 (Story 1.6)**: the Tema segmented control's Home/End/ArrowUp/ArrowDown keys silently changed the selected theme without moving focus, because the internal review's own fix for the Story 1.2 visual-fill gap (rebuilding on React Aria's `ToggleButtonGroup`) introduced a `keyup`-based commit on a component that only manages horizontal-arrow focus and gives every segment `tabindex="0"`. Rebuilt from scratch as a correct APG radiogroup.
  - **PR #8 (Story 1.8)**: the shipped activation gate only protected the *promotion* of a *waiting* worker; while online with a non-empty outbox, a fresh deploy's `index.html` was still served network-first, so a running tab could silently flip to a new shell mid-job and then flip back to the old cached shell the moment it went offline. Fixed by adding a second `hold-shell` mechanism on the *active* worker driven by a live outbox-backlog query.
  - **PR #2 (Story 1.7)**: hardcoded Caddy/api-prod host ports would collide across parallel worktrees — every other host port in the compose file was already configurable, this one wasn't. Fixed with env-parametrized ports.
- **Recurring failure mode**: four of these five defects (Combobox, 5xx-as-password, cross-tenant dedupe, Tema keyboard) share a shape — the internal review found and fixed a *related* issue in the same area, but a second, deeper instance of the same class of bug survived because nothing re-verified the *patch* itself with fresh eyes. This matches the spec's own `followup_review_recommended: true` flag on 7 of 8 stories, and its own stated reasoning in Story 1.2's triage log: "patched... by the same subagent that wrote the original bug, without an independent reviewer re-examining the new code." The independent human/live-verification pass is earning its keep specifically by catching exactly this class of regression.
- **Dev model/effort fit** (from the parallel deferred-work research pass over `## Auto Run Result` sections; not independently re-derived by me, but consistent with what I saw in the diffs):
  - **Story 1.7 (sonnet · medium)** looks under-provisioned: it shipped a new HTTP static-file server with a path-traversal guard — security-adjacent surface — with zero tests in the first pass, caught only because three independent review layers converged on the same gap after the fact. A story touching this kind of surface probably warranted a higher tier than the lowest one assigned to any feature story in the epic.
  - **Story 1.3 (opus · medium)** produced the highest raw finding count of the epic (51) despite the strongest model, at only medium effort, for a story spanning schema + migrations + auth + repositories + two screens + e2e in one shot — plausibly effort-undersized relative to its actual scope (it also independently carries the `oversized` warning).
  - **Stories 1.4 and 1.5 (fable · high)** — the two hardest kernel/sync stories — were correctly given the highest tier, and still surfaced the most medium-severity findings of the epic, suggesting the tier was necessary, not generous.
  - **Story 1.8 (opus · high)**, the largest and most cross-cutting story, correctly got top tier and still needed three high-severity patches — consistent with genuinely being the hardest story, not a mismatch.
- **Cost signal via iteration counts**: none of the eight stories needed a second full dev+review dispatch loop (`review_loop_iteration: 0` throughout) — every finding was patched in-place within one pass. Seven of eight stories flagged `followup_review_recommended: true` regardless, which the independent human review then substantively used (§ above), rather than that flag being pro forma.

## 8. Verdict

**Top 5 strengths**
1. Architecture-spine conformance is real, not aspirational — ten separate AD rules checked directly against code, zero hard violations, with the lint config mechanically enforcing the module-boundary rules rather than relying on review discipline alone.
2. The op-log/`applyOp`/replay-byte-equality machinery (Story 1.4) is unusually rigorous for a "day one" foundation: three independent code paths proven equal against one golden fixture, not just one path tested against itself.
3. Test quality is consistently high: deterministic Playwright patterns ("Sincronizar agora" over timers), a real Drizzle migration-drift test, real axe/contrast assertions, and no hard-coded-value or inert-mock anti-patterns found in the sample inspected.
4. The independent-review layer demonstrably catches what the internal automated review misses, on a recurring and specific failure mode (a patch to one bug leaving a sibling bug in the same area unexamined) — and every one of those catches (cross-tenant dedupe, Host-header trust, three accessibility/keyboard bugs) was fixed before merge, with tests added.
5. Self-documentation quality: comments throughout `apps/api` and `apps/web` cite the specific AD number they satisfy and explain the reasoning, not just the mechanism — this makes the codebase unusually reviewable, which is exactly what let this review move fast and with confidence.

**Top 5 weaknesses**
1. The PRD Q0 real-device offline proof — the one thing the epic's own narrative says gates everything after it — has never been run; the epic is marked `done` in `sprint-status.yaml` regardless.
2. A visible design-system gap (Toggle/Checkbox selected-state fill) has been open since Story 1.2, was worked around rather than fixed for `SegmentedControl`, and remains unowned for the two components it will actually block (Epic 3/5 checklists).
3. One surface (Account's registration save) still bypasses the op log entirely, unconverted despite the op log and its own op family (`user/field`) existing since Story 1.4 — a concrete, if small, offline-first gap in an offline-first epic.
4. Every feature story carried an `oversized` warning — a consistent signal, not a one-off, that story sizing for this build pipeline needs recalibrating.
5. A repeatable pattern of "the fix for bug A quietly introduces bug A′ in the same area, caught only by an independent second look" recurred across at least four of eight stories — currently compensated for by a human/live-verification review step that isn't guaranteed to always be run this thoroughly.
