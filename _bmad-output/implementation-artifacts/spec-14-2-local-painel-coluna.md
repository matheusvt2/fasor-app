## Intent

**Problem:** The location tree is cabine › coluna, so a switchgear line-up cannot be grouped and a masonry room has no Função. Story 14.2 (`epics.md` `### Story 14.2`, criteria blocks of 2026-10-10 and 2026-10-13; the 2026-10-09 block is superseded and must not be built) makes it Local › Painel › Coluna.

**Approach:** Add `kind = painel` and the cabine field `funcao` to the kernel (location row, template skeleton, op path, fold, tree, composer functions, print grouping, status decisions), bump the contract to 17, draw the three levels in the Template composer and the relatório tree from the redrawn mocks, rename the root to "local" in every on-screen string, and print a painel as a heading over its colunas.

## Boundaries & Constraints

**Always:**
- The cabine row stays the root: `kind = cabine`, keeps `se`, `env`, `agrupar_por_tipo`; identifiers, paths and the generated DOCX keep "cabine" and the FO.SERV-03 titles. On screen it reads "local" everywhere.
- A painel is a child of a cabine, carries no data and takes no block. A coluna is a child of a painel; a coluna directly under a cabine (every row and template that exists today, the seeded standard template included) stays valid, is never migrated, and reads, syncs, shows (directly under its local) and prints exactly as before.

## Second pass, 2026-10-13: location removal and restore in the relatório tree; coluna control names

Scope: `epics.md` Story 14.2, block "Acceptance Criteria added 2026-10-13 (location removal in the relatório tree; Matheus, review of PR #126)" with its Definition of Done, plus the naming fix of "Noticed and not fixed" (1) and (2) above. The design below is the coordinator's and is not reopened; where this section and the sections above disagree, this one wins.

### Intent

**Problem:** A coluna, a painel and a local cannot be removed in the relatório tree (O1), and a sheet another device creates in, or moves into, a removed location stays in the snapshot. A coluna's controls are named by the coluna alone, so the default "Coluna 1" of two painéis gives identical names.

**Approach:** One batch of explicit tombstones per removal (no new op path, contract stays 17), planned by a pure kernel function; one derived ancestor rule in the snapshot as the backstop; restore entries per removed location beside the removed sheets; qualified control names composed in the kernel.

### Design

1. **Liveness, one rule.** New kernel helper `liveLocationIds(locations)`: the ids whose row has `removed_at === null` and no removed ancestor among the given rows (walk `parent_id`; an ancestor absent from the input is not "removed"; a parent cycle terminates). `schemas/snapshot.ts` `buildSnapshot` and `createSnapshotBuilder` keep a location only when its id is in that set (computed over every location row of the relatório in the state, removed ones included) and keep a block only when `removed_at === null` and its `location_id` is null, names a live location, or names a row absent from the state (today's behaviour for an unknown id, unchanged; this is the reading of "a block whose location is not live": a row in the state that is removed or has a removed ancestor). `createSnapshotBuilder` keeps its identity guarantees. Every kernel reader that filters raw location rows by `removed_at` itself and can be handed removed rows (`relatorio/tree.ts` `liveLocations`, `relatorio/progress.ts`, `templates/from-relatorio.ts`, `relatorio/move.ts`, any other found by `grep -n "removed_at === null" packages/domain/src`) reads the same helper, so a hand-built input and a snapshot agree.
2. **Re-rooting and progress.** With rule 1 a location under a removed parent is not drawn. The re-rooting in `relatorio/tree.ts` (roots and `firstBlockIndex`) stays only for a parent absent from the input (the op-order bypass of ledger entry (a)); its comment is corrected. `descendantLocationIds` stays structural (the removal plan reads it); `locationProgress` and `locationProgressIndex` count only blocks on live locations, so each drawn node's counter still equals `locationProgress` of that node. Changed test, with this reason: `tree.test.ts` "every counter equals locationProgress of its node, a removed location in between included" asserted that a location under a removed coluna is drawn as a root and still counted under its local; the criterion of 2026-10-13 says the locations under a removed location are absent from the tree and the counters, so the test now asserts the Nicho is not drawn, its sheet is out of the local's counter, and the counter-equals-progress loop still holds.
3. **Removal plan** (new `packages/domain/src/relatorio/removal.ts`, exported from `index.ts`): `locationRemovalPlan({ locations, blocks, otherBlocks, locationId, projectId, relatorioId, visibility })` returns null when the location is not live, else `{ kind, locationId, locationIds, blockIds, equipmentIds, counts: { paineis, colunas, sheets } }`: the location and every live location under it (a removed child and its subtree are skipped), every live block on them, and the equipment each removed block frees by `equipmentFreedByRemoval` evaluated with the other blocks of the same removal taken out of `blocks` (an equipment two removed sheets share is freed once; one a sheet outside the removal or another relatório holds stays). `counts` are the locations under the target by kind and the sheets. The web turns the plan into ops in this order: `location/{id}/removed_at` removes (target first, then tree order), `block/{id}/removed_at` removes, `equipment/{id}/removed_at` removes; one `edit` batch, so every tombstone carries the batch's one `client_ts` as its `removed_at`.
4. **Which removal a row belongs to: the shared timestamp.** `applyOp` writes `removed_at = op.client_ts` for a `remove`, and `buildBatch` stamps every op of a batch with one `now`, so the rows of one removal share one `removed_at` string. The restore reads that equality; no batch id is stored on rows. Accepted limit: two removals stamped in the same millisecond (two devices) restore together. The "Desfazer" of a restore puts the same timestamp back (`invertBatch`), so the group survives an undo.
5. **Restore plan** (same module): `locationRestorePlan({ locations, blocks, equipment, locationId })`, all rows removed ones included; null when the location is not removed. With `T` its `removed_at`: `locationIds` = its removed ancestors (rows alone, root first), itself, and the locations under it whose `removed_at === T`, descending through rows that are live or removed at `T` and stopping at a row removed at another time; `blockIds` = the blocks on those locations (the target, the restored ones and the live ones in between) whose `removed_at === T`; `equipmentIds` = the equipment of those blocks that is not live; `counts` = what becomes visible (restored plus live-but-hidden locations by kind, and sheets). A sheet or location removed at another time stays removed. `removedAncestorIds(locations, locationId)` (the location itself and its ancestors that are removed, root first) also serves `restoreSheetOps`: "Manter a ficha" of a removed-versus-edited decision and any sheet restore put those location rows back with the sheet, so a kept sheet is never restored into a hidden location.
6. **Restore list.** `restorableEntries({ blocks, equipment, locations, since })` in `relatorio/sumario.ts`: a union list, newest removal first, labels unique across the whole list. A removed location is an entry only when `removed_at > since` (or `since` null) and its parent is null or live (rule 1); a removed block is an entry only when its location is null or live. ~~Everything else comes back with its entry, or shows up once its parent is back.~~ *(2026-10-13, review: true for every row a removal tombstoned; not for a sheet another device left live under a location whose removal is older than the newest revision, which stays hidden with no entry.
