## Intent

**Problem:** Nothing in the app creates a Project or a Relatório yet: Home's "Novo relatório" is a permanently disabled stub (`apps/web/src/surfaces/home/home-surface.tsx:137`), the kernel has no `instantiateTemplate`, `suggestTag`, `preIssue`, `progress` or `sheetState`, and there is no surface that shows a relatório as the document the client will read. Every later Epic 4 story (setup, tree, blocks, status, section text, generate) starts from the data model and the Sumário this batch creates.

**Approach:** In the kernel, add the relatório creation batch (`instantiateTemplate` copying the template's skeleton and BlockConfigs into `relatorio` + `location` + `equipment` + `block` creates, section blocks included), the TAG suggestion and uniqueness rules, a fractional `order_key` helper, AD-18 `sheetState`, `progress`, `preIssue` (typed rows, seeded with this story's three families) and `sumarioRows`; make `template.version` increment on every content edit (D-4). In the web app, add three routes built from `30-project.html` and `40-relatorio-overview.html`: the Project surface with its "Novo relatório" Form dialog (Home's "Novo relatório" first asks client and obra through the existing inline-create Combobox), and the Sumário with reorderable section rows, header counts, the section 9 expander (a tracked stub for batch B), the setup placeholder route (tracked stub for batch C) and the "Gerar relatório" hook file (tracked stub for batch D).

## Boundaries & Constraints

**Always:** the kernel computes every status, count, order, title and text once (`packages/domain`), `apps/web` renders only from Dexie and writes only through `commitBatch`/`undoBatch`; ids and timestamps come from the caller (`newId`, `now`), never minted inside the kernel; the creation is ONE `commitBatch` call (one `batch_id`, at most 500 ops, the seeded template yields 1 + 6 + 17 + 11 + 94 + 94 = 223 ops) and the server never copies anything (AR-5); TAG uniqueness is a kernel `integrity` finding against `equipment where project_id = … and removed_at is null`, never a database constraint or a server rejection; every screen uses the mock's class names verbatim and its pt-BR copy verbatim (mock titles win over the AC's abbreviations, e.g. "Recomendações gerais (NR-10)", "Verificações e ensaios aplicáveis"); disabled buttons use `aria-disabled` plus the visible `disabledReason` (`Button` component), never `isDisabled`; every `.frame-*` mock rule first rendered here gets its `app.css` media-query translation in this change with a comment naming the mock rule; every destructive action (Remover, Desfazer, Restaurar) moves focus deliberately and the e2e asserts the focused element afterwards (E3-A8); no emoji, no `laudo`, no client material outside `packages/domain/fixtures/porto-seguro/`; new copy goes in exactly one home (derived text in the kernel, surface copy in `pt-br.ts`, component chrome in `ui.ts`).

**Never:** do not build the Relatório setup page (Story 4.2, batch C), the location tree body or the block palette (4.4/4.5, batch B), status transitions or the Em revisão banner (4.6, batch C), the editable Section text surface (4.7, batch C), the Export dialog, `RelatorioSnapshot` changes for rendering, the generate job or revisions (4.8, batch D); do not add drag-and-drop for Sumário rows (Overflow, Position box and Alt+Up/Down are the required paths; reuse `useReorder` drag only if it costs nothing); do not persist section 9's manual expand state; do not touch `tokens.css`/`components.css` (byte-identical by test); do not enforce location depth; do not add a Dexie schema version (`local_prefs` is generic); do not create a `/project` list surface (projects are reached from Home's "Novo relatório" dialog and from the Sumário's back link); do not write "SEC-C5"-style unpadded TAGs (the fixture's hand-authored tags are data, the rule is zero-padded two digits).
