### Process findings

- **P-1 The single late gate found latent faults, and the fixes that followed it ran with less.** By Matheus's decision of 2026-11-21 ("teste completo somente no final") the epic had one full gate, on `8a214062` (green: unit 7 604, api 1 138, full e2e 769 of 773, matrix 158 of 174, 0 failed). Then #358 and #360 merged, and the shared gate on `64ddc634` was red three ways (`epic-26-context.md` § "the deploy"):
  - **A test-order fault since Story 26.4.** `test-reset.integration.test.ts` empties the test companies' user and role rows; since 26.4 a push by a user with no role row is refused; `template-seed-push.integration.test.ts` never seeded its company and "was green only when a seeding file ran between the two" (#363). The gate on `8a214062` passed by order.
  - **A fragile unit test from e26s** (`session.test.tsx`, 6 of 10 failed alone under load), made deterministic in #364.
  - **WebKit reds in `paused-user-unsent.durability.spec.ts`**, which turned out to be the harness: the session cookie is `Secure`, the e2e origin is plain http, WebKit refuses it; "the file had never run on the matrix projects" (#364 body). e26s had added two cases to that file and ran only `desktop-chrome` and `durability-desktop-chrome` (`spec-e26s-pass-fixes.md` § Gate). That follows the story gate of 2026-10-08, which asks for the matrix when a batch changes the op fold, the commit path or a live query on the ficha (`AGENTS.md`); e26s changed the session and the sync engine's pause handling, which that wording does not clearly name, so a new case in a durability-named spec fell between the rules.
  The decision was kept and the final gate (`886af55e`) was green, so the outcome is sound; the cost was a red gate on a shared commit, three fix PRs and a wait. Lesson: when a fix batch follows the epic's one full gate and changes product code, either its touched specs include every matrix project they touch, or the full gate runs again before the deploy. Matheus chose "Teste inteiro no final, somente" for the final gate, and the gate on `886af55e` was green; E26-A7 records the rule for fix batches.
- **P-2 The review's fix produced the blocker the pass then found.** #358 item 1 (reactivate ends sessions) made R-4 possible; its own trace 6(a) said so in the PR body and handed it to the owner as "a product question". The hands-on pass then found it as a blocker. The sequence worked (review, pass, fix, in one day), but the trace's conclusion was not turned into a fix or a test in the same batch. Lesson in E26-A7.
- **P-3 Update-path blind spot, found in production (#369).** Home's new "Usuários" shortcut drew no icon on the owner's phone right after the v0.13.0 deploy: `/sprite.svg` was one path for every build and the old worker answered it cache-first, so any release that added a sprite symbol showed it blank on the first launch after the update. Reproduced on unmodified main with the real worker (PR #369 body); fixed with a content-hashed sprite, six worker tests and `e26u-E2E-001`. The pass ran on fresh loads, so no test or pass could see it; every earlier symbol added since the worker shipped had the same defect. It is a defect of the product's update path that Epic 26 happened to expose. Fixed; covered since by `e26u-E2E-001`. Accept; record in E26-A7 that the browser pass on a deploy candidate includes one launch over the previous build.
