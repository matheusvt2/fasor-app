### Diff-scope review (three lenses over e21f, `fdc19924..8252cee4`)

**R-1. A model's group entry can be replaced by an uncited composed one and then dropped.**
- Confirmed. Raised by all three lenses: ADV 1, ECH 1 and VG 1.
- Where: `vector-diagram.ts:124-131`, then `bedrock.ts:273-274` (`withoutUncitedValues`).
- The path:
  - The model gives a group entry citing known OCR ids that is not "printed", for example "Dy1" citing "H1".
  - The diagram facts compose, but every id they cite is unknown to the OCR read.
  - The fold filters those ids to known ones, which leaves `[]`, and still replaces the model's entry with the composed value.
  - `withoutUncitedValues` then drops it, and the field gets no suggestion.
- Before e21f, the same answer became a `verify` diagram read.
- This is the residue of e21f's own first triage row: "cites only labels the OCR returned; none left is uncited and dropped next" fixed the citation and left the replacement.
- No test pairs an existing entry with an all-unknown diagram. The tests at `vector-diagram.test.ts:65`, `:102` and `bedrock.test.ts:490` have no group entry.
- The real set did not hit it (0 wrong), so it is Low.
- Disposition: **fix now** (E21-A1): when no known id is left, keep the model's entry. Test it through `withoutUncitedValues`.

**R-2. The "printed" verdict lives in three places, and the eval's copy disagrees with the kernel.**
- Confirmed; ADV 6 and 14.
- `printsItsGroup` (`vector-diagram.ts:91-104`) re-implements in `apps/api` the kernel's rule (`reading/build.ts`). It skips the kernel's value normalization.
- `groupRead` (`bedrock-eval.ts:254-260`) filters cited ids to known tokens. The kernel drops an entry citing any unknown id (`unknown_token`), so the eval can print a code, or "(diagram)", for a reading the job stores as nothing.
- The paid eval is this story's deploy evidence, so its table must read what production stores.
- Disposition: **fix now** (E21-A1): one exported kernel predicate, used by `buildReadingSuggestions`, the fold and `groupRead`.

**R-3. The fold's outcome is silent.**
- Confirmed; ADV 3.
- `withVectorDiagram` returns `rest` for malformed facts, for facts that do not compose, and for a printed entry that wins, with no log line. The facts are stripped before `reading_run` is written (`vector-diagram.ts:114-122`).
- In production, a wrong or missing group cannot be traced to its cause: the facts, the composer or the citations. That is the question e21f was opened to answer.
- Disposition: **fix now** (E21-A1): one `reading vector diagram` log line with the outcome and the four shape facts (no OCR text).

**R-4. The fake fixture schema lost the unique-key check.**
- Confirmed; VG 2 and ADV 10.
- `fakeStructuringFixtureSchema` (`fake.ts:52-57`) replaced `structuringOutputSchema` and dropped its "each key at most once" refine (`contract/ocr.ts:167-173`). The committed-fixtures test (`fake.test.ts:63`) therefore no longer catches a duplicate key. It surfaces only as a `PermanentReadingError` when a test structures that fixture.
- Also, `fake.ts` now imports `withoutUncitedValues` from `bedrock.ts`, which pulls the Bedrock module graph into the fake-only path.
- Disposition:
  - the refine: **fix now** (E21-A1);
  - the import: **fix now**, by moving the helper into a provider-neutral module and re-exporting it from `bedrock.ts`.

**R-5. The escalation model gets the new schema and was never measured on it.**
- Plausible; VG 3 and ADV 5.
- The production default `bedrock_escalation_model_id` is `us.amazon.nova-pro-v1:0` (`infra/production/variables.tf:75-78`).

- Escalation runs only on a plate more than half `verify`, so it is reached rarely.

**R-6. Prompt and schema wording that a model other than the probed Haiku may misread.**

**R-7. "Printed wins" depends on OCR fidelity.**
- Plausible; ADV 2 and 7.

- On the real set, one of the five Dyn1 reads came back as a diagram read. A drawn-only plate or a garbled print would both explain it, and the run does not say which.

### Process lessons

**P-1. The batches prepared the paid eval, and only the coordinator's run found the defect.**
- Story 21.2's spec put the eval outside the batch: "Never run `bedrock-eval.ts` (paid); only prepare it" (`spec-e21r` Never), and "the run is a deferred 'before the deploy' row".
- Every fake-provider test of the drawn plate passed, because the fixture's structuring answer *is* the expected value. The fake replays "Yyn0", so the test checks the plumbing (build, `verify`, the note, the confirm) and never the reading.
- The coordinator's paid run on `fdc19924`, after both batches had merged, read the drawn Yyn0 plate as Dy1 3 of 3 (`epic-21-context.md` § Paid eval). That cost:
  - a fix batch (e21f, PR #256) after the integrated review;
  - a second gate (lock wait 1 120 s);
  - a fix that no review re-read (R-1).
- The real set was not on the machine at the time. It came from the production bucket on 2026-11-06, after the deploy.
- Lesson: a story whose AC depends on what a model perceives (plate, display, caption, diagram) runs its paid eval inside the batch, before its PR merges, on the synthetic set and on a real set fetched into git-ignored `docs/media/` first. The eval table is merge evidence beside the gate. Fake tests are named as plumbing tests in the spec. The paid run is the coordinator's, with Matheus's AWS login, because the batches never hold a paid key, as Policy requires (E21-A4).

**P-2. Composing a symbolic code inside the prompt failed; describing facts and composing in the kernel worked.**
- The model "perceives the diagram right but composes the code wrong": asked for the code, it answered Dy1 3 of 3; asked for facts, it answered the right facts 5 of 5 (`spec-e21f` Problem). With `composeVectorGroup` doing the composition, the drawn plate read Yyn0 3 of 3 on `bedrock-structuring-4`, and the real set read 0 wrong.
- This is AD-13 applied to model output: the kernel computes every code and verdict once, and the model reports what it sees.
- Lesson: a reading prompt that needs a derived value (a group code, a class, a verdict) asks the model for the perceptual facts and lets a kernel function compose them. It is recorded as a design rule in the playbook and the KB, and proposed to Matheus as a dated line in the architecture spine (E21-A4, E21-A5).

**P-3. Load flakes came back, three times in one epic.**
- e21p's story gate: 6 web unit failures at load 23.5 while e21r worked on the same VM. One file (`setup-surface.test.tsx`, lost typing) failed twice, then passed alone (PR #254 § Story gate).
- e21r's pre-merge gate at load 26: `reading-arrivals.test.tsx`, `template-composer-local.test.tsx` and R8DRY-E2E-005 were red, and green alone (PR #255).
- The integrated gate on `fdc19924` ran while the integrated review's own stack (`fasor-e21q`) and a Playwright MCP browser worked beside it for about 25 minutes, at load 4.5 to 5.2:
  - `reading-arrivals.test.tsx` and `home-surface.test.tsx` (12.2 "Continuar") were red;
  - R8LAY-E2E-008 was red;
  - all three were green alone, the e2e after a lock wait of 790 s (`epic-21-context.md` § Integrated gate).
- R8LAY-E2E-008 was already "red once in 5" on 2026-11-04 (`docs/kbs/log.md`, chore T2). `home-surface.test.tsx` flaked in Epic 12 (`epic-12-retro-2026-09-25.md:73`). `reading-arrivals.test.tsx` was red in two gates of this epic.
- None of these files has a ledger row or an owner.
- The rules held: the reruns were recorded with both runs (E15-A4), every gate carries its load line (E18-A3), and `test:e2e:full` was green on `8252cee4` before the deploy (E18-A6). The cost was the reruns and the lock queue.
- Lesson:
  - the integrated review's stack and browser do not run during the integrated gate's `test:unit` and `test:e2e*` stages;
  - a test red under load in two gates of one epic gets a ledger row and a hardening owner (E21-A4).

**P-4. The fix batch after the review got no re-read.**
- § 6 of the playbook asks for "a re-check by the same QA agent through SendMessage" after the fix batch.
