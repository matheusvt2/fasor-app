## Intent

**Problem:** Home is still the Story 1.3 placeholder paragraph and Account has no theme or storage row, so a user who opens the app in the field cannot see which relatórios exist, which of them are on this device, or what state the queue is in. The kernel has no `relatorio/status` transition table, the Sync badge never announces, only one of the seven banner slots is populated, no Toast component exists, and the Story 1.2 selectable controls (SegmentedControl, Toggle, Checkbox, grouped FilterChipGroup) never show their on state in a browser.

**Approach:** Add the kernel modules this surface reads from — `packages/domain/src/status` (the AD-22 `(state, event) → state` table, `editedSince`, the status display vocabulary) and `packages/domain/src/home` (status-board counts, ordered Home cards with every line of text, device availability) — then rebuild Home and Account from them on the Story 1.2 components and the mock's class names. Complete the shell: the badge gains the short word, an explicit accessible name and a transitions-only live region; the banner slot gains the "+N" chip and the offline candidate; a Toast component and provider arrive; Account gains the Tema segmented control persisted in `local_prefs` and the storage row. The on-state gap is closed by rebuilding `SegmentedControl` on React Aria's `ToggleButtonGroup`, whose visible button carries `role="radio" aria-checked` — exactly the attribute `components.css` already targets — with no edit to the mock CSS.

## Boundaries & Constraints

**Always:** `packages/domain` stays pure (zod only) and computes every status, count, order and user-visible text once: `statusTable` is the only emitter/decider of `relatorio/status` transitions, `syncCounts`/`syncBadgeState`/`syncBadgeLabel` are the only source of badge state and words, `statusBoardCounts` and `homeCards` are the only source of the board counts, the card order and every card line. `apps/web` renders those results and never derives a status, count, order or label from a row. `apps/web` reads only through `useLiveQuery` over `src/db`; Dexie is imported only inside `src/db`; `fetch` only under `src/{sync,files,api}`. `tokens.css` and `components.css` are byte-identical copies of the mockups and stay untouched (`src/styles/styles.test.ts` enforces it); anything the mock has no selector for is authored in `src/styles/app.css` using existing tokens only. Screens use the mock's class names; `DESIGN.md`/`EXPERIENCE.md` win over a mock on conflict. Disabled controls use `aria-disabled` plus an `aria-describedby` reason, never React Aria `isDisabled`; every tap target is at least 48px (56px for field controls). pt-BR copy comes verbatim from the mocks or `EXPERIENCE.md`; anything else is marked `// authored:`. English identifiers, no emoji, no `fasor` in `apps/web/src`, `PRODUTO` from the kernel constant. Dexie `VERSIONS` is append-only; adding a non-indexed field to a row interface needs no new version. Everything runs through `docker compose` (project from `{WT}/.env`).

**Never:** No edit to `tokens.css` or `components.css`, and no new class name invented inside them. No change to the sync contract in `packages/domain/src/contract` and no new or changed API route — the server is untouched by this story. No `relatorio/status` op is emitted by any surface here (Setup and Export own the emitters in Epics 4 and 7); this story ships the table and its tests only. No relatório detail route, Sumário, Templates or Cadastros surface, and no relatório creation (Epics 2, 3, 4): the affordances that point at them render disabled with a reason. No progress counter ("n de N fichas") and no counted "Baixando… n de m": both need `progress(snapshot)`, which does not exist (AD-8; Story 1.5 deferred the summary field). No conflict banner or Conflict view, no merge policy (Epic 10) — the badge keeps the `conflict` word without ever producing the state. No `draft-found`, `suggestions-ready`, `relatorio-exported` or `unsynced-5-days` publisher (Stories 1.8, Epics 7 and 8 own them); the slot mechanism carries all seven kinds. No service worker (Story 1.8). No file upload or photo (Epic 6): the photo count in the storage line reads from the local `files` table, which is empty. No `localStorage` mirror of the theme. No Login rework.

## Design Notes

**The on-state gap is closed by changing the component, not the CSS.** `components.css:701` styles `.segmented .seg[aria-checked="true"]` on the visible element, and Story 1.2 built `SegmentedControl` on React Aria `RadioGroup`/`Radio`, which renders a `<label class="seg">` wrapping a hidden native `<input type="radio">`; the state never reaches the styled element, and mirroring `aria-checked` onto the label is an `aria-allowed-attr` violation once the input owns the role. Story 1.2 also verified the other half of the picture: React Aria's `ToggleButtonGroup` in single-selection mode renders each `ToggleButton` as a real `<button role="radio" aria-checked="…">` — which is exactly the mock's own markup and exactly what the existing selector targets. Rebuilding `SegmentedControl` on `ToggleButtonGroup` therefore makes the fill engage with zero CSS change and zero axe violations, and the test asserts the attribute on the visible element so a future React Aria change cannot silently regress it. If that assertion fails on the installed version, the sanctioned fallback is a hand-rolled radiogroup (`<div class="segmented" role="radiogroup">` with `<button class="seg" role="radio" aria-checked>` children, roving tabindex, arrow-key and Home/End handling) — the mock's markup verbatim. Editing `components.css` is not an option under any outcome; if it ever looked necessary, that is a spec decision to record with evidence, not a patch. `Toggle`, `Checkbox` and the grouped `FilterChipGroup` keep the same gap and the Story 1.2 deferred entry: none of them is used by Home or Account, and rebuilding them is not this story's scope.

**The status-board tile has no mock state at all.** `components.css` carries `.status-board`, `.status-tile` and `.tile-count.is-zero` and nothing for a pressed tile — the mock's tiles are plain navigation buttons, while `EXPERIENCE.md` and UX-DR63 require `aria-pressed` filtering. The pressed look is therefore authored in `src/styles/app.css`, the project's own stylesheet (precedent: `.sync-badge-btn` from Story 1.5), reusing the segmented control's selected treatment and existing tokens so the two read as one system. `components.css` stays byte-identical.

**Every line of a Home card is kernel text.** AD-2 forbids `apps/web` from deriving a status, count or text, so `homeCards` returns view models whose `title`, `meta` and `device.text` are already strings; the surface only places them in the mock's elements. That is also what makes the ordering rule (current card first, then service start descending, then id) testable without a browser, and what lets the "Baixando…" text gain its counts later in one kernel function.

**Cards the device has never downloaded come from the company summary.** The pull response's `summary.relatorios[]` is the only place a relatório in Em revisão or Emitido appears before it is pulled, and Story 1.5 read it and dropped it. Persisting it on the company `sync_state` row (a non-indexed field, so no Dexie version) gives Home the "Não está neste aparelho" card and gives `syncRelatorio(id)` something to act on; the engine's existing "every relatório that already holds a `sync_state` row" rule then keeps it fresh, which is AD-8's "pulled on open" with no new route.

**"Baixando… n de m" ships without its counts.** AD-8 says the counts come from the company summary's per-relatório `progress(snapshot)`, and Story 1.5 deferred that field because `progress` is an Epic 5 kernel function. Inventing a substitute would mean either a contract change this story's Boundaries forbid or a number in seq units that is not a count of anything a user recognises. The kernel emits "Baixando…" alone, the counted form is one string change inside `homeCards` when the field lands, and the deferral is recorded.

**Affordances without destinations render disabled, not hidden.** "Continuar", "Ver sumário", "Novo relatório", Templates and Cadastros are all required by the AC and all point at surfaces Epics 2, 3 and 4 own. AD-23 already gives the honest rendering: `aria-disabled` with an adjacent reason linked by `aria-describedby`, still focusable. One authored reason string is shared by all five so the screen never argues with itself.

**Theme lives in the user's database.** The AC says `local_prefs`, which is the per-user Dexie store, so the override applies once the database opens — during `Booting`, before Home paints — and Login follows `prefers-color-scheme`. `themeAttribute` returning null for "Sistema" (remove the attribute) is what makes `tokens.css`'s `:root:not([data-theme="light"])` dark block take over again; writing `data-theme="system"` would silently pin light.

**`syncCounts` keeps its Story 1.5 signature.** Story 1.6's AC and test 1.6-UNIT-002 write it as `syncCounts(snapshot, outbox)`, but no snapshot exists until Epic 5 and the sheet and photo counts are already derived from op paths. Adding an unused parameter now would be speculative; the existing `syncCounts(outbox)` satisfies the test's substance and the signature change is recorded as deferred against the story that first has a snapshot.

**`unsynced-5-days` is a slot, not a publisher, here.** The banner copy "Alterações sem envio há 5 dias" belongs to Story 1.8's acceptance criteria, and `unsyncedForDays` already exists for it. This story ships the seven-kind priority, the "+N" chip and the `offline` candidate; the remaining five kinds stay declared and unpublished with a comment naming their owner.
