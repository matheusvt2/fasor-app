# Story delivery

- A story is ready only with acceptance criteria, definition of ready and definition of done in `_bmad-output/planning-artifacts/epics.md` (a new story is written there; the stories of the closed Epics 1 to 30 are in `epics-archive.md` beside it, and an epic moves there once it is closed). Implementation stays inside what the story says. Every story carries `**Dev model:** ... · **Effort:** ...`; `_bmad/custom/bmad-build.toml` reads it to pick the subagent `bmad-dev-<model>-<effort>`. Add the line to every new story.
- Main receives only merged pull requests, self-approved (record the review verdict as a PR comment). Never force-push a branch; merge origin/main into it. Until 2026-11-12 the unit was one branch (`story/<sprint-status-key>`) and one squash-merged PR per story.
- Since 2026-11-12 (Matheus, token economy; `AGENTS.md` "Decisions of record"): the unit is the wave. One batch and one PR per wave (two only when kernel and screen work do not touch), named by its batch tag (for example `e32-wave`) and merged with a merge commit; one review per wave; one full gate per wave on the integrated branch; one records PR per wave. The batch still runs `lint`, `static`, `test:unit`, `test:api` and its touched specs before its PR.
- Flow: build (`bmad-build-auto`), PR with verify output, independent review in a fresh context, fixes, gate ([merge-gate](/workflow/merge-gate.md)), merge, then flip the story to `done` in `sprint-status.yaml`.
- Per epic: stories are batched by shared surface, run with isolated worktrees and compose projects, then one integrated QA, one fix PR, a retrospective (`epic-N-retro-*.md`, in the epic's folder `_bmad-output/implementation-artifacts/epic-NN/`). Playbook: `_bmad-output/implementation-artifacts/epic-batch-orchestrator.md`. Carry-over items go to `deferred-work.md`. *(2026-11-24: a row that closes moves to `deferred-work-archive.md` under the same heading; the ledger keeps only open, partially closed and in-progress rows.)*
- Definition of Ready capability check (2026-10-14, E14-A4): every verb a criterion asks of a surface (remove, move, restore) is checked against what the surface does today and the open `deferred-work.md` rows; a missing capability becomes named scope with its own criteria before the build. Test rules (2026-10-14, E13-A7): a browser API with a fallback gets an e2e stubbing it to reject and to hang (`e2e/plate-shot-fallback.spec.ts`); a capture e2e asserts a property of the captured file. Both in the playbook, sections 4 and 6.
- Cross-batch merge rule (2026-10-15, Story 14.10 part 2): before the second batch PR of a wave merges, the first batch's branch (or main after it merged) is merged into it and both batches' touched specs run on the result; only then does it merge. PRs #137 and #133 were green alone and together turned 14.2-E2E-002 red (fixed in #138). Playbook section 6.
- Retro rules in the playbook (2026-10-28 and 2026-11-03): § 7 carries the Epic 15 to 17 rules (seed-bump literal grep, a red-under-load stage re-run alone with both runs in the PR, restart the api after a kernel change, lint and static after review patches, gate logs in `.scratch-<tag>/`, a batch's last steps as a script, "facts the batches share"); § 8 the Epic 18 ones: a residual risk that changes how a view or document is read is a runbook sentence in the same PR, every wave gate record carries the host load line, and `test:e2e:full` green on an integrated main is recorded before its deploy ([merge-gate](/workflow/merge-gate.md)). § 9 (2026-11-04, E20-A4): the integrated review is two passes, a behavior pass and a code read of every "patched, not re-reviewed" list; a batch with no spec and no sprint-status line records its verification-gap read in the PR body; a budget or quota rule ships with restore and shrink tests. Ledger rows owned by "the next epic's carry-over batch" are read when that batch is cut (§ 6, E6-A7). § 11 (2026-11-11, E23-A3 and E24-A3) carries fourteen lines from the Epic 23 and Epic 24 retrospectives: the hands-on pass runs, with its report tracked, before any deploy of an integrated main; a change to a printed table carries a test that reads the PDF and a crop; a story that adds a field lists the entity's readers and writers; deploy after the wave's fix batch; a PR that bumps a reading prompt carries its eval table; the plan says whether waves overlap fix batches, and a gate's record is written when the gate ends and names what else ran on the host; a batch that reads the test base checks its diff for the base's word runs; a broken word or number in a golden or a PDF is a defect row with an owner batch; the last product-code commit before a deploy gets a read; the PR body lists the grep over `e2e/` and the web tests with its hits; one Auto Run Result line per orchestrator cut; the deploy record closes or carries each "before the deploy" row by name; the questions for the field engineer go out when the stories are written.
- Built record of each story or batch: a `spec-*.md` file. It is written at the root of `_bmad-output/implementation-artifacts/` while the epic is in work and moves into the epic's folder, `_bmad-output/implementation-artifacts/epic-NN/`, when the epic closes (2026-11-28); that folder also holds `epic-N-context.md` and the retrospective. Records of no single epic (review-fix batches, production-pass fixes, chores) go in `_bmad-output/implementation-artifacts/general/`. `sprint-status.yaml`, `deferred-work.md`, their archives, `epic-batch-orchestrator.md` and `reviews/` stay at the root. A sprint change proposal goes in `_bmad-output/planning-artifacts/sprint-change-proposals/`.
- Pitfalls: the coordinator must not pull into the owner's main checkout without care (uncommitted edits); `gh pr merge` needs the owner's go-ahead when the classifier denies it; push branches before long gates.
