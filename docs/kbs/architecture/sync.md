# Sync, session, tenancy

- **Cycle (AD-24)**: push ops, upload files, pull company, pull each relatório. `POST /api/sync/ops` takes up to 500 ops and answers `{applied, rejected, superseded}`; one rejected op never blocks the rest. The server rejects only for shape (`op_invalid`, `op_path_unknown`), server-only family (`op_server_only`), tenant mismatch (`op_tenant_mismatch`) or ownership (`op_forbidden`); ~~never for a domain rule. - A rejected op becomes `outbox.status = dead` with its code, is excluded from materialized state, keeps its value for "Reenviar", and is listed by pre-issue. Retry: network and 5xx with backoff; 4xx never, except `401` (re-auth banner, outbox intact) and `409 file_row_missing`.
- Pull returns `{ops, seq, summary?}`. The relatório stream is a query (ops with that `relatorio_id` plus project-scope ops of its project, `seq > since`), never a stored fan-out. Rebase: after a pull, pending outbox ops are re-applied on top.
- **Offline (AD-8)**: a service worker precaches the shell so a cold open works offline. No install prompt, no Background Sync, no reliance on `persist()`. The engine runs only while the tab is open: on launch, on `online`, every 60 s. Automatic pull: every relatório in Rascunho or Em campo, company scope, `thumb` variants; Em revisão and Emitido on open. Banner when outbox items are older than 5 days; warning under 500 MB free storage. A visible "Sincronizar agora" action exists (decision 2026-09-21); tests use it instead of the timer.
- **Session (AD-9)**: the api serves the built web bundle same-origin, no CORS. better-auth email plus password, httpOnly `SameSite=Lax; Secure` cookie, 30-day sliding. Sign-in needs connectivity; the session continues offline. Dexie database is `releng-{user_id}`; ~~sign-out never drops it~~ *(2026-11-04, Story 20.11: a confirmed sign-out flushes, confirms the unsent count, deletes it, then the pointer; a 401 at boot lands on Login without opening it; offline only an existing database opens)*. *(2026-11-04, Story 20.13: only sign-in, sign-out and get-session reach better-auth (`AUTH_ROUTES`); every mutating `/api` request passes `http/origin-guard.ts` (trusted `Origin` or `Sec-Fetch-Site: same-origin`, JSON body) or gets `403 forbidden_origin`. Story 20.12: `ai_usage_daily` caps readings and audits per company per day, `429 quota_exceeded`.)* Users are provisioned by a seed CLI (`pnpm seed:users`); no signup, no outbound email.
- **Tenancy (AD-10)**: `company_id` on every Drizzle table; every repository function takes it as a required typed argument. The kernel schemas carry it only on `op` and `file`.

- **Badge "Tentando de novo" (Story 14.10 lane B, 2026-10-15)**: after a cycle that ended unreachable (network or 5xx) with the browser online, the engine probes `GET /api/health` (`client.health()`, 5 s abort, true on any HTTP answer, false on a network failure or the abort) and publishes `EngineStatus.serverAnswers`. The kernel `syncBadgeState` then reads `retrying` ("Tentando de novo", short "Tentando") instead of `offline`; order conflict, error, browser offline, retrying, unreachable offline, pending, ok. A clean cycle resets the answer; a later unreachable cycle keeps it until its own probe answers. A session to renew stays "Sem conexão". Sync status names the cause (`copy.sync.serverRetrying`). The Home cards take the same answer (`homeCards` input `serverAnswers`). No client timeout on the sync requests themselves: a slow request in flight keeps the previous word until it fails.
- **A sheet edit is sent by itself (Story 25.3, batch e25a, 2026-11-11)**: every local commit announces itself once from `apps/web/src/db/commit.ts` (`announceCommit`, `sync/commit-signal.ts`); the sync provider coalesces the announcements in a fixed 2 s window (`COMMIT_SYNC_WINDOW_MS`, `followCommits` in `sync/nudges.ts`) into one `engine.nudge()`, and the page turning visible and Sync status opening nudge too (`followVisible`, `requestSyncCycle`). While files upload, the engine pushes pending ops before each file attempt after the phase's first (`pushBetweenFiles` in `engine.ts`, single-flight, ops in `client_ts` order; a failure stops it for the rest of the cycle, a re-auth or outdated ends the upload phase). File transfers are bounded: an upload waits at most `requestHeadersTimeoutMs(blob.size)` for its answer's headers, a download `SYNC_REQUEST_TIMEOUT_MS` for its headers then `fileBodyTimeoutMs` for its body (`client.ts` `send`); an abort is a `network` failure for the upload retry table. The badge gains `late` ("Envio atrasado", short "Atraso"): an op `pending` or `sent` for strictly more than 60 s (`SYNC_LATE_AFTER_MS`, `lateOpCount`, `syncLateAt`, `syncLateText` in `packages/domain/src/sync/late.ts`) while online, reachable and not paused; order conflict, error, offline, retrying/unreachable, late, pending, ok. Sync status shows the kernel's line with "Sincronizar agora" beside it (`.e25-late`). The 60 s tick, the retry table and the phase order are unchanged.
- **A commit asks for a push only (fix batch e25x, 2026-11-12)**: the coalesced commit window calls `SyncEngine.pushNow`, a push-only pass: the pending ops are pushed and nothing else runs (no pull, upload, thumb, eviction, prune or sweep, no `sync_result` event); `EngineStatus.pushing` is true while its request is open and `running` stays a full cycle's. A pass and a cycle never overlap (a cycle waits for the pass; a commit during a cycle gets one pass after it); a 401 pauses and a 426 flags outdated as in a cycle; a failed pass sets `lastFailure` and holds later passes until a full cycle starts. A window that saw a file commit (`announceCommit('file')`, a certificate or any non-photo file) asks for one full cycle instead, so the bytes upload. Full cycles keep their moments: launch, `online`, the 60 s tick, the page turning visible, Sync status opening, "Sincronizar agora", a photo capture. The late wait is counted per op on the monotonic clock (`state/late-ops.ts`), and the instant the device became able to send is taken during render. `spec-e25x-wave1-web-fixes.md`.
