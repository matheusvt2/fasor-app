# Suggestions and reading

**Suggestion (AD-12)**: entity `{id, relatorio_id, target_path, value, trust suggested|verify, mode fill|replace, source {photo_id, bbox normalized, ocr_token_ids, reading_run_id}, status pending|confirmed|discarded, prompt_version}`. The reading job emits only `pending` creates. Every sheet cell is `{value, source_suggestion_id|null, op_id}`; any later plain `put` clears the source. "Confirmar" is one batch: `suggestion/{id}/status = confirmed` plus the target value with `meta.source_suggestion_id`. "Confirmar todos" skips `verify`. On applying a suggestion whose target cell is non-empty, the device runs `compareSuggestion`: equal -> auto-confirm batch with `meta.auto = true`; different -> stays pending as `replace`. Pending is the stored status, never inferred; progress, pre-issue, counts and renderer ignore anything not confirmed. A value is `suggested` only if it passes digit coverage over the OCR tokens the model cited, else `verify`; checked on the server. Derived suggestions (conclusion, parecer, deadline) are kernel computations, not rows.

**Reading pipeline (AD-14)**: a photo carries `reading_kind` (plate, display, caption, panel, nc_obs) and `reading_target`, set on the device at capture; `reading_status` is written by `system:reading` ops. File receipt enqueues one pg-boss `reading` job, singleton `(photo_id, reading_kind)`, three attempts then `failed`; `POST /api/photos/{id}/reread` re-enqueues. Two steps behind two interfaces in `domain/src/contract/ocr`: `OcrProvider.read(image)` returns tokens with bboxes, then the LLM structuring step. **The LLM never emits coordinates**; every bbox comes from OCR, the model only cites `ocr_token_ids`. Each run stores a `reading_run` row (provider, model, prompt_version, usage, duration).

Providers by environment: `LLM_PROVIDER` in fake, bedrock (Story 11.6 dropped `anthropic`); `OCR_PROVIDER` in fake, textract, ocr-svc. Both default to `fake`, which replays fixtures from `apps/api/src/jobs/reading/fixtures` so dev, tests and compose need no cloud or key. The backend never uses a personal Claude subscription. Real providers are post-MVP and behind a flag (Story 11.8, AI features off in production until Story 11.6 is merged, deployed and the flag applied in `infra/`).

**Bedrock (Story 11.6, 2026-10-05)**: `providers/bedrock.ts` is one Converse adapter behind both `StructuringProvider` (plate, panel) and `ProseProvider` (caption, NC draft), credentials from the AWS SDK default chain only, one lazily built client per process, `maxAttempts: 1` (pg-boss retries). Structured output is Converse tool use (`record_values` / `record_text`, forced with `toolChoice`), the tool schema derived from the `FieldDef`s, the input validated with `structuringResultSchema` / `proseResultSchema`; OCR tokens go as `t<n>: text` lines, never coordinates. A reply without the tool call or failing the schema is permanent; `AccessDeniedException`, `ValidationException`, `ResourceNotFoundException` and any other non-retryable client fault are refused (`ProviderRefusedError`, permanent); credential errors, throttling, 5xx and the 60 s timeout are transient. Since the review fixes of 2026-10-08 (C4) the Converse client layer, the error classes, `classifyAwsError` and `callWithTimeout` live in `apps/api/src/ai/` and serve Bedrock (reading and audit, one client per process built in `main.ts`) and Textract alike; the audit records a refusal as `provider_refused`. `prompt_version` constants `bedrock-structuring-2` (dates as precise as printed, pt-BR separators spelled out) and `bedrock-prose-1`; USD from `BEDROCK_PRICES` (2026-10-05 us-east-1 list prices; a model missing there fails at boot). Settings: `BEDROCK_REGION` (us-east-1), `BEDROCK_MODEL_ID` (Claude Haiku 4.5, `global.anthropic.claude-haiku-4-5-20251001-v1:0`), `BEDROCK_PROSE_MODEL_ID` (defaults to the structuring model), `BEDROCK_ESCALATION_MODEL_ID` (Amazon Nova Pro, `us.amazon.nova-pro-v1:0`; empty disables).

**Units and years as printed (review fixes 2026-10-08, AIR-1, AIR-V1, PLN-13)**: `normalizeReadingValue(field, value, cited)` moves a plate number printed in another unit of the field's quantity into the field's unit (`convertReadingUnit`/`parseSiUnit`, kernel `reading/units.ts`: "13.800 V" on a kV field is 13,8 kV, "1,5 MVA" is 1500 kVA), takes the unit from the cited tokens when the model gives none, prefers the printed pt-BR number when the model kept a thousands dot (Verificar), and returns `printedText` so the digit rule reads the value as printed. A conversion whose factor nothing printed grounds is Verificar: a model unit the cited tokens do not print whose power is not the field's, or a model unit the print contradicts (the model pair is kept); a voltage class given as a bare number takes the volt unit its cited tokens print (independent review of PR #115). A bare plate year ("2012") is suggested and stored as is, the shape the typed path stores (the OCR contract text still says `YYYY-MM[-DD]` until its next change, `deferred-work.md`); a typed year over a date suggestion goes through `parsePlateDateText` with the F-22 range (`parseFieldInput(field, text, {now})`). The synthetic TP plate prints "13.800 V" and "2020" to exercise both (`e2e/plate-units-years.spec.ts`).

**Escalation (Matheus, 2026-10-05)**: a plate reading whose suggestions are more than half `verify`, or that has none (`shouldEscalate`, kernel `reading/escalate.ts`), is structured once more on the escalation model, and `betterReading` keeps the one with more `suggested` values, then the one with more rows, then the escalation's (the stronger model; Matheus, 2026-10-06, a cascade's usual rule). `shouldEscalate(rows, ocrWords)` is false when the OCR found no word, since a second model has nothing to cite; the run row names the kept model with the usage of both calls summed (`kinds/plate.ts`). A failed escalation call keeps the first reading with its own usage. No escalation provider is built when the escalation model is empty or equals `BEDROCK_MODEL_ID`, nor any Bedrock provider while `AI_FEATURES=off`. Panel, caption and NC draft never escalate. Panel fronts read on their own model, `BEDROCK_PANEL_MODEL_ID` (Qwen3 VL 235B by default; Matheus, 2026-10-06), chosen in the factory by `reading_kind`; plates stay on `BEDROCK_MODEL_ID`. The manual evaluation `apps/api/src/scripts/bedrock-eval.ts` (never run by verify) compares candidates on field accuracy, valid citations, tokens and USD; choosing a cheaper default waits for real nameplate photos.

**Emission audit coverage (Story 14.10 lane B, 2026-10-15)**: `auditInput` (`packages/domain/src/audit/input.ts`) sends the sheets holding a value before the empty ones (`sheetState` `vazia`), each subsection's heading and local parts with the first pass, and writes a sheet line as `[sheet:<id>] <printed title> (<screen label>)` when the two differ. It reports `sheetsSent` (sheet lines inside the `AUDIT_INPUT_MAX_CHARS` cut) and `sheetsTotal` (sheets the layout prints); the job stores them as `audit_run/{id}/coverage` `{sent, total}` in its done batch (contract 20) and logs `sheets_sent`/`sheets_total`. The Export dialog and the Sumário show `auditCoverageText` ("Conferidas 2 de 76 fichas"); a run older than contract 20 parses with `coverage: null` and shows none. A standard relatório's ~95 empty sheets are more than the cap carries, so its runs read e.g. 25 of 95.

**Emission audit out of date, fixed rules (Story 25.24, 2026-11-12, contract 52)**: the job freezes the snapshot under the company lock (`freezeSnapshot`, as the generate job does) and writes `audit_run/{id}/snapshot_seq` with the done batch. The device marks the newest finished run out of date with `auditRunStale` (`audit/text.ts`, over `editedOnDevice` and `apps/web/src/db/generate-store.ts` `streamOpsSince`; a run with no point, written before 52, reads as out of date) and shows the warning Banner with "Conferir de novo" over the old findings at 72 %; the check never runs by itself. `audit/rules.ts` `auditRuleRows(snapshot)` lists three fixed rules beside the findings, marked "Regra": a stored result looser than the floor (`conclusionFloorReasonText`), the same run of three or more measured values in the same order on the same test of two equipment of one type (not a run of one repeated value), and a row voltage the winding does not support (the sheet's `rowVoltageNotice`). Prompt `audit-2` adds the kind `observation_vs_items`; the fake's selector `sheet-citing:<text>` points it at the sheet whose lines carry the text. Rules and findings stay information: nothing in `print/` or the pre-issue rows reads them.


**The v18 plate options (Story 28.3, 2026-11-23, batch e28a, contract 58)**: the structuring prompt is `bedrock-structuring-10`. Its options still come from the seed: a v18 transformer lists "A SECO | A ÓLEO" and CONSTRUÇÃO's two options, with notes for the dry option and for CONSTRUÇÃO (only as printed); a v18 TP and TC list ÓLEO VEGETAL. The kernel lands an older spelling on its option through the aliases (ÓLEO ISOLANTE as "A ÓLEO", EPÓXI as "A SECO") and composes "A ÓLEO" from a printed oil class. The OCR schema did not change. The paid eval (`apps/api/src/scripts/bedrock-eval.ts`) waits for Matheus's word.

**A tool input member sent as JSON text (batch e28v, 2026-11-23)**: in the paid eval of prompt 10, Haiku 4.5 twice sent the drawn Yyn0 plate's `values` as a string holding the JSON array, and the strict parse made the reading a permanent failure. Before the vector-diagram fold and the contract parse, `withDecodedJsonMembers` (`providers/bedrock.ts`) replaces each array or object member of the tool input that arrives as a string (`values`, each entry, an entry's `ocr_token_ids`, `vector_diagram` and its `ocr_token_ids`) by its JSON parse when that parse has the member's shape, and logs one `reading structuring tool input decoded` line (model, member paths, no plate content). Anything else stays as it came and the same strict `structuringResultSchema` judges it; a value's own text and a whole tool input sent as a string are never decoded. Prompt and `prompt_version` unchanged. *(2026-11-24, batch e28v2: the paid rerun after #375 still failed, and the captured input showed the `values` text was the tool object's body from `values` on, the array then `,"vector_diagram": {...}`, with no top-level `vector_diagram`. When the `values` text does not parse on its own, `{"values":<text>}` is tried and lifted to the top level only when it is a plain object of `values` (an array) and at least one other tool member (`vector_diagram`), none of them also at the top level; an unknown key or a conflict stays a permanent error. The log's member path is `values+vector_diagram`.)* A permanent error of the first structuring call fails the reading without trying the escalation model, which runs only after a successful first reading that `shouldEscalate`.

**Voice input (AD-30, 2026-11-26, Epic 31, planned, not built)**: the device only records; an `audio` file with `audio_target`, `audio_status` and device-measured `quality` rides the file queue; a `transcription` job (`STT_PROVIDER` fake or transcribe, then a writing step on Bedrock, both `fake` by default) writes prose straight into the field (`meta.source_audio_id`, the one exception to "nothing unconfirmed is written") and emits a pending Suggestion for a measurement reading; `writtenTextGuard` falls back to the text as heard; a pending or failed audio holds the ficha and the issue; audio is never purged. The AI control is the online route `POST /api/relatorios/{id}/write`. Read `### AD-30` in the spine.
*(2026-11-26, batch e31a, Stories 31.1 and 31.2, contract 62: built as far as the server.)* A Suggestion's `source` is a photo's or `{audio_id}` (`isPhotoSuggestionSource`, `suggestionPhotoId`, `photoSourceOf`; a crop is drawn only for a photo source). The `transcription` pg-boss queue (`apps/api/src/jobs/transcription/`: `worker.ts`, singleton per audio, three attempts, a dead letter that fails a still-`transcribing` audio; `job.ts`; `status.ts`, actor `system:transcription`) starts on the upload of a `queued` audio (not while `AI_FEATURES=off`) and on `POST /api/audios/{id}/retranscribe` (from `failed` only, the field's key, 404 across companies). Speech by `STT_PROVIDER` (`fake` replays `fixtures/speech.json`; `transcribe` refuses to boot until Story 31.8), writing by `LLM_PROVIDER` (`fake` replays `fixtures/writing.json`; `bedrock` through Converse, prompt `transcription-write-1`, `prompt.ts`). Prose targets get the kernel's write in one batch with `meta.source_audio_id`; a guard failure or a writing call failing for good writes the text as heard; a table's parsed reading is a pending Suggestion (`audio-reading-1`), other speech goes to OBSERVAÇÕES with `not_a_reading`. Each attempt stores a `transcription_runs` row (migration `0008`). The job re-reads the creator's role and fails the audio when it no longer holds the field's key.
*(2026-11-26, batch e31c, Stories 31.5 and 31.6, no contract change.)* A spoken reading renders exactly as a display reading (`measurementSuggestions`, auto-confirm when equal, "Confirmar todos"); `suggestionAudioId` picks play over the crop, `audioMismatchText` reads "Sugerido: 147 GΩ". `audioWrittenTarget` sends a table's `not_a_reading` audio to its ficha OBSERVAÇÕES for the mark; `audioForTarget` also returns `failed`, `dismissed` and the table's `moved`. `audio/hold.ts`: `heldAudios` (queued, transcribing and, by the coordinator's reading, failed), `heldAudiosText`, `audioPlaceText`, `audioSheetStep`, `audioSyncCounts`, `audioSyncLines`; `preIssue` adds the blocking rows `audios_pending` and `audios_failed` (row 9, each audio with its place), so the server's generate refuses them too.
